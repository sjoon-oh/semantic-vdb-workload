# semantic-vdb-workload

벡터 DB 근사 캐싱 실험을 위한 **의미적 지역성 + Zipf 편중 합성 워크로드 생성기**입니다.
기준 질의마다 비슷한 질의 그룹을 만들고, 그룹 위에 Zipf 편중 스트림을 얹고, 스트림 사이에
삽입/삭제를 끼워 넣은 뒤, 모든 질의의 **정확한 정답(ground truth)** 을 함께 만듭니다.

> 상태: 도구와 테스트까지 구현되었습니다. 실제 데이터셋(예: SIFT 1M)으로 워크로드를 생성하는
> 실행은 아직 하지 않았습니다. 이 도구가 만든 워크로드는 **합성 데이터**이며 실제 질의 로그의
> 통계를 대변하지 않습니다.

## 무엇을 만드나 (예시)

1. 공개 질의가 1만 개 있습니다 (원본 질의).
2. 원본 질의마다 비슷한 질의 `group_size`(기본 200)개를 만듭니다. 풀은 1만 × 200 = 200만 개입니다.
   `group_size = 50, 200` 처럼 목록으로 적으면 크기마다 풀을 하나씩 만듭니다. 변형이 시드와 얼마나
   가까운지를 정하는 `target_overlap` 도 `0.8, 0.5` 처럼 목록으로 적으면 겹침마다 풀을 따로 만듭니다
   (노이즈 크기 α가 겹침마다 다릅니다). 풀은 **겹침 × 그룹 크기**의 조합마다 하나이고
   (디렉터리 `o80/g50`, `o80/g200`, `o50/g50`, ...), 각 풀에 아래의 갱신 비율 세트를 모두 만듭니다.
3. 한 워크로드 세트의 전체 요청 수 `total_requests`(예: 100만)는 **읽기 + 갱신의 합계**입니다.
   갱신 1건은 **삽입 1 + 삭제 1** 이므로 삽입 수와 삭제 수는 항상 같습니다.
   갱신 비율 `p`%이면 갱신 = `total_requests × p / 100`, 읽기 = 나머지입니다.
   `update_percents = 0, 25, 50` 이라고 적으면 세트 `u0`, `u25`, `u50` 을 한 번에 만듭니다.

   | 세트 | 읽기 | 삽입 | 삭제 | 읽기:갱신 |
   |---|---|---|---|---|
   | `u0` (읽기 전용) | 1,000,000 | 0 | 0 | 100 : 0 |
   | `u25` | 750,000 | 250,000 | 250,000 | 75 : 25 |
   | `u50` | 500,000 | 500,000 | 500,000 | 50 : 50 |

4. 읽기 요청의 스트림은 종류가 둘입니다 (아래 "스트림 종류"). 기본은 Zipf 스트림으로, 요청마다 그룹을
   Zipf 인기도로 고르고 그 그룹의 구성원 하나를 균일하게 뽑습니다. 같은 벡터가 여러 번 나올 수
   있습니다(정확 반복).
5. 읽기와 갱신을 `num_steps` 단계로 나누고, 단계마다 삭제 → 삽입 → 질의 순서로 진행합니다.
6. 각 질의의 정답은 **그 단계의 삭제와 삽입이 모두 반영된 활성 집합** 기준으로 계산합니다.
   삭제와 삽입이 같으므로 살아 있는 벡터 수는 내내 base 크기와 같습니다.

## 구조: 베이스 세트 + 워크로드 세트

```text
<output_dir>/<base_set_name>/                 # 공유되는 베이스 세트 (인덱스도 한 번만 빌드)
  base_set.json  base.<ext>  base_row_ids.ibin
  insert_pool.<ext>  insert_row_ids.ibin
  query_rows.<ext>  query_row_ids.ibin        # num_query_rows > 0 일 때만
  workloads/<workload_name>/                  # 한 번의 생성이 만드는 묶음
    family.json                               # 풀·겹침·세트의 색인과 공통 지문 (경로, 읽기/삽입/삭제 수, workload.json 해시)
    build_report.json                         # 단계별 소요 시간과 해석된 병렬 설정 (해시 대상 아님)
    build_report_extension_1.json ...         # 묶음에 풀을 추가한 실행마다 하나 (아래 "묶음에 풀 추가")
    shared/                                   # 다음 실행이 다시 쓰는 결과 (아래 "공유 결과 shared/")
    o80/  o50/ ...                            # 겹침 목표마다 하나 (o<백분율>: 0.8 → o80, 0.125 → o12p5)
      g50/  g200/ ...                         # 그룹 크기마다 풀 하나
        u0/  u25/  u50/ ...                   # 갱신 비율마다 세트 하나. 각 디렉터리가 혼자서 완결됨
          workload.json                       # 파라미터, 읽기/삽입/삭제 수, α 보정, 진단 값, 모든 파일의 sha256
          pool/pool.<ext>  pool/pool_group_id.ibin  # 질의 풀과 그룹 id
          seeds.<ext>                         # 원본 시드 질의 (external 모드에는 없음)
          eval_query.<ext>                    # 평가 질의
          stream_zipf_<s>/step_00001.<ext> ...    # 단계별로 실행되는 질의 벡터
          stream_zipf_<s>/step_00001.group_id.ibin  # 각 질의가 속한 그룹
          stream_uniform_unique/step_00001.<ext>    # (uniform_unique = true 일 때) 중복 없는 균등 스트림, 같은 배치
          updates/delete_step_00001.ibin ...  # 단계별 삭제 id (삭제가 있는 단계만)
          groundtruth/stream_zipf_<s>/step_00001.bin
          groundtruth/eval/step_00000.bin ... # step 0 = 갱신 전 초기 상태
    g1/u0/ ...                                # given 질의(variants = none): 노이즈가 없으므로 겹침 단계가 없음
    external/u0/ ...                          # 외부 그룹(seeds mode external): 같은 이유로 겹침 단계가 없음
```

- 같은 베이스 세트를 쓰는 세트들은 **같은 삽입 순서의 앞부분**을 각자 필요한 만큼 소비합니다.
  그래서 갱신 비율이 다른 세트도 한 인덱스를 공유합니다. 삭제 대상은 갱신 비율마다 한 번 뽑습니다
  (같은 비율의 세트는 풀이 달라도 같은 벡터를 지웁니다).
  베이스 세트의 삽입 풀은 **가장 큰 갱신 수**(위 예에서는 50만)를 감당해야 하며, 모자라면 생성 전에
  어느 세트가 얼마나 모자란지 알려주며 실패합니다.
- 한 묶음 안에서 **한 번만 계산해 공유하는 것**: 시드 이웃 탐색, PCA (모든 풀이 공유), 노이즈 크기 α
  (**겹침마다** 한 번: 같은 겹침의 풀들은 같은 α), 평가 질의. Zipf 스트림은 풀마다 지수마다 한 번만 뽑아 두고, 각 세트는 그 **앞부분**(읽기 수만큼)을
  씁니다. 그래서 `u50` 의 읽기 50만 개는 `u0` 의 앞 50만 개와 같고, 갱신 비율만 다른 짝지은 비교가
  됩니다. 같은 seed 로 그룹 수가 같으면 풀 사이에서도 **그룹의 방문 순서가 같습니다** (구성원만 다름).
  겹침이 달라도 같은 그룹 크기의 풀은 같은 그룹·같은 구성원 번호를 같은 순서로 요청합니다 (벡터만 다름).
- **내용이 같은 파일은 하드링크**입니다 (링크가 안 되는 파일시스템이면 복사): 풀 파일은 같은 풀의
  모든 갱신 비율 세트에서, 시드·평가 질의는 묶음 전체에서, 삭제 id와 평가 정답은 같은 비율의 모든 풀(겹침이
  달라도)에서 한 파일입니다. `cp -r` 로 세트 하나를 옮기면 독립된 복사본이 됩니다. 도구는 이 파일을 수정하지
  않으므로, 직접 고치지 마세요 (하드링크라 다른 세트도 바뀝니다).
- 갱신이 0인 세트(`u0`)는 활성 집합이 변하지 않으므로 평가 질의 정답을 step 0 한 번만 만듭니다.
- 이미 있는 베이스 세트/묶음 디렉터리는 **절대 덮어쓰지 않습니다** (`FileExistsError`). 묶음에는
  새 풀만 **추가**할 수 있습니다 (`[workload] existing = extend`, 아래 "묶음에 풀 추가").
- 빌드는 `<name>.building` 에서 하고 **묶음 전체**가 끝나면 이름을 바꿉니다. 실현 가능성 검사는
  데이터를 읽기 전에 모든 세트에 대해 먼저 하며, 여기서 실패하면 흔적을 남기지 않습니다.
- **중단되어도 이어서 합니다.** 단계를 하나라도 끝낸 뒤에 중단되면(Ctrl-C, 오류, 강제 종료, 정전) `.building`
  이 남고, **같은 명령을 다시 실행하면 끝난 단계는 건너뛰고 이어서 합니다** (아래 "중단과 재개").
  끝낸 단계가 없으면 예전처럼 흔적을 지웁니다.

### 중단과 재개

워크로드 빌드는 단계를 끝낼 때마다 `<name>.building/_resume/` 에 완료 표시를 남깁니다. 표시는 그 단계의 파일이
모두 디스크에 쓰인 **뒤에** 만들어지므로, 중간에 끊긴 단계는 표시가 없어 처음부터 다시 합니다.

| 단계 (표시 이름) | 내용 | 재개 단위 |
|---|---|---|
| `seed_neighbours` | 시드마다 베이스에서 가장 가까운 `neighbours` 개 (베이스 스캔) | 단계 |
| `n2_bases` | 시드별 PCA 기반 (끝나면 `shared/cache.json` 에 sha256 기록) | 단계 |
| `calibration_<o..>` | 한 겹침의 노이즈 크기 α 보정 | 겹침 |
| `pool_<o..>_<g..>` | 한 풀의 변형 생성과 통계 (겹침 재측정, 베이스 스캔) | 풀 |
| `common`, `eval_step0` | 세트들이 공유하는 파일, step 0의 평가 정답 | 단계 |
| 우주 스캔 (`stream`, `eval`) | 질의를 묶음(`QUERY_GROUP_ROWS`)으로 나눠 우주를 훑음 | **질의 묶음** (묶음마다 `<이름>_done/` 표시) |
| `mix_<u..>` | 한 갱신 비율의 모든 풀 세트 | 갱신 비율 |

- **다시 실행하면** 저장된 지문(설정, 베이스 세트의 id 해시, 질의 파일의 내용 해시)을 먼저 비교합니다.
  같으면 이어서 하고, **다르면 지우지 않고 무엇이 다른지 알려 주며 멈춥니다.** 처음부터 다시 하려면
  `<name>.building` 디렉터리를 직접 지우세요. `[parallel]` 설정은 결과에 영향을 주지 않으므로 지문에 넣지 않습니다
  (GPU에서 시작해 CPU로 이어도 정수형 데이터에서는 같은 파일이 나옵니다. float 데이터는 배치 크기가 같아야 하며 다르면 멈춥니다).
- 이어서 만든 결과는 한 번에 끝낸 빌드와 **파일이 바이트 단위로 같습니다** (테스트로 확인). 풀 생성의 난수는
  모두 설정의 seed에서 나오기 때문입니다. 끝난 세트와 이어서 만든 세트가 공유하는 파일도 하드링크로 하나입니다.
- `build_report.json` 의 `resumed_from_stages` 에 이어받은 단계가 적힙니다 (그 단계의 시간은 `stage_seconds` 에 없음).
- 재개되지 않는 것: 베이스 세트 빌드(`base-set`)는 중단되면 처음부터 다시 합니다. 실행 중이던 **미완성 단계**
  (예: 풀 하나를 만드는 중, 갱신 비율 하나를 쓰는 중)는 그 단계의 처음부터 다시 합니다.

## 공유 결과 `shared/`

끝난 묶음은 **다시 쓸 수 있는 비싼 결과**를 `<묶음>/shared/` 에 남깁니다. 풀 하나를 더 만들 때 이것을 계산하지
않고, 어느 세트 하나가 지워져도 추가가 가능하게 하려는 것입니다.

| 경로 | 내용 | 크기 |
|---|---|---|
| `shared/n2/` | 시드의 정확한 이웃(`seed_neighbour_ids/dists.npy`)과 시드별 PCA 기저(`basis_axes/std/residual.npy`). 기본 세트 전체 스캔이라 가장 비쌈 | 시드 1만 개에 약 0.3 GB [계산: 100차원 256 MB + 이웃 40 MB, 128차원은 328 MB + 40 MB] |
| `shared/cache.json` | 위 파일의 **sha256과 지문**(시드 벡터, 기본 세트, `neighbours`, `axes`), **겹침마다 α 보정 결과**(목표, 허용 오차, α, 달성한 겹침, 반복 횟수, 보정에 쓴 설정) | 작음 |
| `shared/common/` | 시드 질의와 평가 질의 (모든 세트에 하드링크) | 작음 |
| `shared/eval_step0/`, `shared/mixes/<u..>/` | step 0 평가 정답, 갱신 비율마다의 삭제 id와 평가 정답 (모든 세트에 하드링크) | 추가 용량 0 |
| `shared/mix_info/<u..>.json` | 평가 정답 중 직접 훑어서 만든 것의 수 (세트의 `workload.json` 에 들어감) | 작음 |

- 저장된 이웃과 기저는 **쓰기 전에 검사**합니다. `cache.json` 의 지문이 지금의 시드·기본 세트·설정과 다르거나
  파일의 sha256이 다르면 (바뀌었거나 손상됨) **멈추고 알려 줍니다** (`N2Error`). 조용히 쓰지 않습니다.
- 저장된 α 는 그것을 찾은 설정(목표 겹침, 허용 오차, 보정 질의 수, `residual`, seed)이 지금과 같을 때만 씁니다.
- 풀 벡터와 Zipf 스트림은 저장하지 않습니다 (세트에 이미 있고, 스트림은 seed와 그룹 크기에서 즉시 다시
  만들어집니다). `stream_groundtruth = true` 의 스트림 정답 목록도 풀마다 달라서 저장하지 않습니다.
- `shared/n2` 가 없는 묶음(지웠거나 `variants = none`/`external`)에 풀을 추가하면 이웃과 기저를 다시 계산하고
  묶음에 저장합니다.

## 묶음에 풀 추가 (`[workload] existing = extend`)

이미 끝난 묶음에 **새 겹침이나 새 그룹 크기의 풀만** 더할 수 있습니다. 기본값 `existing = error` 는 이전과
같이 묶음이 있으면 멈추고 아무것도 건드리지 않습니다. 추가는 명시적으로 켭니다.

```ini
[workload]
name = spacev1b_100m_workload     ; 이미 있는 묶음의 이름
existing = extend
[groups]
group_size = 100, 200, 400, 1000  ; 400, 1000 이 새로 생김
target_overlap = 0.8, 0.5         ; 0.5 가 새로 생김
```

그러면 도구는 설정의 조합(겹침 × 그룹 크기)과 `family.json` 의 풀을 비교해서 다음을 합니다.

1. 이미 있는 풀은 **건너뜁니다** (`[extend] the pool o80/g100 exists: skipped`). 건드리지 않습니다
   (파일, 크기, 수정 시각, inode 불변: 테스트로 확인).
2. 새 풀만 만듭니다. 이웃·PCA·평가 정답·삭제 id는 `shared/` 에서 가져오므로 (평가 정답은 새 세트에 하드링크)
   **새 풀의 생성·통계·파일만** 비용이 듭니다. 이미 있는 겹침에 그룹 크기만 더하면 α 보정도 없습니다.
3. 새 풀과 이미 있는 풀이 **함께 정한 것**이 하나라도 바뀌었으면 거부합니다: 시드·`num_groups`, `[groups]` 의
   나머지(`neighbours`, `axes`, `residual`, `include_original`, 보정 질의 수, 허용 오차), `[stream]`, `[updates]`,
   `[evaluation]`, `[groundtruth]`, 기본 세트, 질의 파일의 내용. 오류 메시지가 무엇이 어떻게 달라졌는지
   (`groups.axes: was 4, now 3`) 알려 주며, 그런 변경은 **새 이름의 묶음**으로 만들라고 안내합니다.
   `[parallel]` 과 묶음 이름은 비교하지 않고, 도구 버전도 비교하지 않습니다 (세트마다 `workload.json` 에 기록).
   질의 파일과 기본 세트가 **어디에 있는지**(경로)도 비교하지 않고 **무엇이 들어 있는지**만 비교합니다 (데이터를 옮기거나
   다른 머신에서 추가해도 됩니다).
4. 형식 2 이전의 묶음(`g100/u0/...`, 겹침 단계가 없음)은 추가할 수 없습니다 (오류: 새 이름으로 다시 만드세요).

**추가가 끝난 묶음은 한 번에 만든 묶음과 같습니다.** 추가해서 만든 묶음이 처음부터 모든 풀을 한 번에 만든
묶음과 모든 파일, `workload.json`, `family.json`, `shared/cache.json` 이 같음을 테스트로 확인합니다
(`stream_groundtruth = true` 에서는 `distinct_query_vectors` 가 "이번 실행이 만든 풀" 기준이라 다릅니다.
같은 겹침의 풀끼리 정답 목록을 빌려 쓰는 정도를 세는 `pool_rows_*` 도 풀 구성에 따라 다를 수 있습니다. 이 둘은
진단 값일 뿐이고 정답 파일을 포함한 모든 데이터 파일은 항상 같습니다).
`family.json` 의 풀·세트는 설정의 순서(겹침, 그룹 크기, 갱신 비율)로 정렬되고, 설정에 더 이상 없는 풀은 지우지
않고 뒤에 둡니다.

**중간에 끊겨도 묶음은 반쯤 바뀐 상태가 되지 않습니다.**

- 새 풀은 묶음 옆의 `<이름>.extending/` 에 만들고 묶음은 그동안 건드리지 않습니다. 끊기면 같은 명령이
  끝난 단계부터 이어서 합니다 (`resume`).
- 다 만들면 **journal**(`<이름>.extending/journal.json`: 옮길 풀, 새 `shared/cache.json`, 새 `family.json` 의 내용)을
  먼저 쓰고, 새 풀 폴더를 묶음으로 옮기고, 보고서를 쓰고, **`family.json` 을 마지막에 원자적으로 교체**합니다.
  그러므로 `family.json` 에 이름이 있는 풀은 완전합니다. 옮기는 도중에 끊기면 같은 명령이 journal 을 보고
  나머지를 끝냅니다 (각 단계는 반복해도 같은 결과).
- 묶음에 `family.json` 에 없는 풀 폴더가 이미 있으면 (누군가 만든 것) **덮어쓰지 않고** 멈춥니다.
- 동시에 두 번 추가하지 못하게 `<이름>.extending.lock` 에 프로세스 번호를 적습니다. 살아 있는 프로세스의 잠금이면
  거부하고, 죽은 프로세스의 잠금은 교체합니다.
- 실행 기록은 `build_report_extension_<n>.json` 에 (새로 만든 풀, 건너뛴 풀, 단계별 시간).

## 정답(GT)을 만드는 방법: 우주 목록

정답은 **요청이 실행되는 시점의 활성 집합**(base + 그때까지 삽입한 것 − 삭제한 것) 기준의 정확한
top-k 입니다. 세트마다, step마다 활성 집합 전체를 다시 훑으면 비용이 `세트 수 × step 수` 에 비례하므로,
다음과 같이 한 번만 훑습니다.

1. **우주** = base + 묶음의 모든 세트가 삽입하는 벡터 (가장 많이 삽입하는 세트 기준). 모든 세트의
   활성 집합은 우주의 부분집합입니다.
2. 어디서든 한 번이라도 요청되는 **서로 다른 질의 벡터**마다 우주를 한 번 훑어 가까운 순서(거리, 같으면
   작은 id)로 상위 `K` 개의 목록을 만듭니다. `K` 는 활성 집합이 우주에서 차지하는 비율로 자동 계산합니다
   (예: base 100만 + 삽입 50만이면 `stream_k = 10` 에 `K = 44`, `eval_k = 100` 에 `K = 214`;
   목록이 모자랄 확률이 10⁻⁹ 이하가 되는 가장 짧은 길이).
3. 어느 세트의 어느 step이든 정답은 그 질의의 목록에서 **그 step에 살아 있는 항목만** 남겨 앞 `k` 개를
   읽어 만듭니다 (아직 삽입 전이거나 삭제된 것은 건너뜀).

이것은 정확합니다. 전체 순서를 부분집합으로 제한해도 순서는 그대로이고, 부분집합의 원소 중 목록의
마지막보다 앞서는 것은 모두 목록 안에 있기 때문입니다. 살아 있는 항목이 `k` 개 미만인 요청은 그 step의
활성 집합을 직접 훑어(fallback) 답하므로, 목록이 짧아도 **느려질 뿐 틀리지 않습니다**. 직접 훑은 횟수는
`workload.json` 의 `groundtruth` 항목에 기록됩니다 (기본 설정에서 0 이어야 합니다).

그룹 크기가 여러 개일 때 작은 풀의 벡터가 가장 큰 풀의 같은 그룹·같은 번호의 벡터와 **바이트 단위로
같으면** 그 풀의 목록을 같이 씁니다 (검증하고 공유하며, 다르면 그 벡터만 따로 계산합니다). 그래서 그룹
크기를 하나 더 늘려도 GT 비용이 거의 늘지 않습니다.

## 파일 형식

| 파일 | 형식 |
|---|---|
| 벡터 `*.u8bin` `*.i8bin` `*.fbin` `*.f16bin` | `[uint32 행 수][uint32 열 수]` + row-major 값 (확장자가 원소 타입을 정함) |
| id 목록 `*.ibin` | `n × 1` 의 int32 |
| 정답 `*.bin` | `[uint32 질의 수][uint32 k]` + int32 id (질의 수 × k) + float32 거리 (질의 수 × k) |
| 매니페스트 `*.json` | 정렬된 JSON (타임스탬프 없음) |

정답의 거리는 `l2` 이면 제곱 L2, `ip` 이면 내적의 부호를 뒤집은 값(작을수록 가까움)입니다.

## id 규칙과 단계 규칙

- 초기 base 의 `i` 번째 행은 id `i`, 삽입한 `j` 번째 벡터는 id `num_base + j` 입니다. 삭제해도 id 를
  다시 쓰지 않습니다. (SPFresh 는 삽입 배치의 첫 VID 를 현재 벡터 수로 정하므로 순차 삽입이면 같은
  번호를 받습니다 [코드 확인]. 여러 스레드가 동시에 삽입하면 보장되지 않으니 `AddIndexReportingFirstVID`
  로 실제 번호를 기록해야 합니다.)
- 한 단계 안의 순서는 **삭제 → 삽입 → 질의** 입니다. 삭제 대상은 그 단계의 삽입 **직전** 활성
  집합에서 균일 무작위로 뽑으므로, 같은 단계에 삽입된 벡터는 그 단계에서 삭제되지 않습니다.
- 동점 거리는 **작은 id 가 먼저**입니다 (CPU 와 GPU 가 같은 결과를 냅니다).

## 그룹 생성: N2

시드 `q` 의 이웃 `neighbours` 개로 PCA 를 하고, 상위 `axes` 개 축으로만 노이즈를 줍니다.

```text
q' = q + α · Σ_j  z_j · std_j · axis_j ,   z_j ~ N(0, 1)
```

- 평균이 `q` 이므로 특정 이웃 쪽으로 치우치지 않고, `axes` 차원 부분공간 안에서 양쪽으로 흩어집니다.
- `α` 는 직접 정하지 않습니다. `target_overlap`(변형과 시드의 top-10 정답이 평균 몇 개 겹치는가;
  0.8 = 10개 중 8개)을 정하면 도구가 이분 탐색으로 `α` 를 찾습니다. 시드 중 `calibration_queries`
  개로 찾고, 보정 후 **전체 시드**에서 실제 겹침과 `d1` 거리비(변형의 최근접 거리 / 시드의 최근접
  거리)를 다시 재서 `workload.json` 에 적습니다.
- `target_overlap = 0.8, 0.5` 처럼 목록으로 적으면 **겹침마다 α를 따로 찾고** 풀을 따로 만듭니다.
  겹침이 작을수록 α가 큽니다 (더 멀리 흩어짐). 한 겹침의 α는 **같이 만드는 다른 겹침과 무관합니다**
  (보정 시드와 난수가 겹침 값에 의존하지 않음): 겹침 `0.5` 를 `0.8` 과 함께 만든 풀은 `0.5` 만 따로 만든
  풀과 파일 단위로 같습니다 (테스트로 확인). 이웃 탐색과 PCA는 겹침 수와 무관하게 한 번입니다.
  `variants = none` 과 `external` 은 노이즈가 없어서 겹침 목록이 무시됩니다.
- 결과는 원래 dtype 으로 반올림·클리핑되고, **정답은 반올림된 벡터 기준**입니다.
- **한계 (가정):** 이웃들끼리 달라지는 방향이 같은 항목의 의역 방향과 비슷하다는 것은 검증되지
  않았습니다. 같은 부분공간을 공유하므로 그룹이 매끄러운 타원체 모양이 되고, 이 저차원 구조를
  이용하는 캐시는 실제에 없는 이득을 보일 수 있습니다.

## 스트림 종류

한 세트에는 여러 스트림이 함께 들어가며, 같은 세트의 스트림은 모두 같은 풀·같은 갱신 스케줄을 씁니다.

| 스트림 (디렉터리) | 설정 | 편중 | 정확 반복 | 의미적 유사 | 쓰임 |
|---|---|---|---|---|---|
| `stream_zipf_<s>` | `[stream] zipf_exponents` | 있음 (지수 `s`) | 있음 | 있음 | 기본 워크로드. 지수 0 이면 편중 없는 균등 + 복원 추출 |
| `stream_uniform_unique` | `[stream] uniform_unique = true` | **없음** | **없음** | 있음 | 정확 일치 캐시 히트가 0 이므로 근사 캐시의 **순수 효과**를 본다 |

- `uniform_unique` 는 풀 전체에서 **복원 없이 균등**하게 뽑습니다. 모든 요청이 서로 다른 벡터입니다.
  예: 그룹 1만 × 200, 읽기 100만이면 그룹당 평균 100번(74~129) 요청되고 그룹 재방문 비율은 0.990 입니다
  [계산, 시뮬레이션].
- 편중과 "중복 없음"은 함께 성립하지 않습니다 (Zipf 0.99 의 1위 그룹은 요청의 약 10% 를 받는데 구성원은
  200 개뿐). 그래서 `uniform_unique` 는 균등입니다.
- 읽기 수가 풀 크기(그룹 수 × `group_size`)를 넘으면 데이터를 읽기 전에 실패합니다. 가장 긴 세트(갱신
  비율이 가장 작은 세트)가 기준입니다.
- 모든 스트림은 지수(또는 종류)마다 한 번 뽑아 두고 세트가 앞부분을 쓰므로 `u50 ⊂ u25 ⊂ u0` 입니다.
- 매니페스트의 스트림 항목에 `kind` (`zipf` / `uniform_unique`)가 있습니다.

### 주어진 질의 그대로 (`[groups] variants = none`)

노이즈 변형을 만들지 않고 **주어진 질의 자체가 풀**입니다 (그룹 하나 = 질의 하나, `group_size` 는 1).
N2 이웃 탐색과 `α` 보정은 하지 않습니다. 현실감을 위해 가공 없는 질의만 쓰는 대조군이며, 공개 질의는
서로 독립이라 근사 히트가 거의 없을 것으로 예상되지만 [추론] 측정하지 않았습니다.

| 하고 싶은 것 | 설정 |
|---|---|
| 합성 의미 그룹 + 편중 | `variants = n2`, `zipf_exponents = 0.3, 0.6, 0.99` |
| 합성 의미 그룹, 중복 없음 | `variants = n2`, `uniform_unique = true` |
| 주어진 질의를 중복 없이 한 번씩 (한 번 훑기) | `variants = none`, `zipf_exponents = none`, `uniform_unique = true`, `total_requests` ≤ 질의 수 |
| 주어진 질의를 반복 허용 균등 추출 | `variants = none`, `zipf_exponents = 0` (정확 반복이 지배적) |

주의: SIFT 공개 질의는 약 1만 개 [미확인]입니다. 100만 요청을 만들면 같은 질의를 평균 100번 반복하게
되므로(정확 반복 약 99%), 중복 없는 버전은 질의 수 이하의 `total_requests` 에서만 가능하며 이때 갱신 수도
같은 비율로 작아집니다.

## 시드 출처 (`[seeds] mode`)

| 모드 | 입력 | 설명 |
|---|---|---|
| `public_queries` | 질의 파일 | 파일의 질의가 시드. `num_groups = all` 이면 질의마다 그룹 하나 |
| `base_rows` | 베이스 세트의 예약 행 | 공개 질의가 없을 때. 베이스 세트를 `num_query_rows > 0` 으로 만들어야 함 |
| `external` | 벡터 파일 + 그룹 id 파일 | 다른 곳에서 만든 의미 질의(예: 의역 임베딩). 교란 없이 skew 만 부여. 평가 질의는 `eval_file` 필수 |

`external` 모드의 base 는 **같은 임베딩 모델**의 벡터여야 합니다 (차원·dtype 은 검사하지만 정규화
여부는 검사하지 않습니다).

## 평가 질의

`evaluation.source = original` 이면 원본(교란 없는) 질의 전체를 씁니다. 평가 질의는 삽입/삭제 중
recall 흔들림을 재기 위한 것이며, 캐시 경로를 타지 않는다는 전제입니다. step 0(초기 상태), 매
`checkpoint_every` 단계, 마지막 단계에서 정답을 계산합니다. 시드와 평가 질의가 같은 질의일 수 있으므로,
이후 파라미터 튜닝에는 이 워크로드의 질의를 쓰지 말고 seed 가 다른 별도 워크로드를 만들어 쓰세요.

### 스트림 질의의 정답 끄기 (`[groundtruth] stream_groundtruth = false`)

기본(`true`)은 스트림 질의(Zipf·`uniform_unique` 요청)마다 그 요청이 실행되는 단계의 정확한 정답도
계산합니다. 이것이 빌드 시간의 대부분입니다 (서로 다른 질의 벡터마다 우주를 한 번씩 훑음).
`false` 이면 다음처럼 바뀝니다.

- 스트림 정답(`groundtruth/stream_*/`)을 만들지 않고, 스트림 질의 파일(`step_xxxxx.<ext>`,
  `.group_id.ibin`)과 삭제 id, 풀, 평가 정답은 그대로 만듭니다 (`true` 일 때와 바이트 단위로 같음, 테스트로 확인).
- 우주 스캔은 평가 질의에 대해서만 합니다. 평가 정답(`groundtruth/eval/`)은 위와 같이 step 0,
  `checkpoint_every` 단계, 마지막 단계에서 그 단계의 삭제·삽입이 반영된 활성 집합 기준으로 계산합니다.
- `workload.json` 의 `groundtruth.stream_groundtruth` 가 `false` 이고, 스트림 목록에 관한 항목
  (`stream_list_length`, `distinct_query_vectors`, `pool_rows_*`, `stream_requests_answered_by_scan`)은 `null` 입니다.
- `stream_k` 는 무시됩니다.

## 정확 반복 진단

`workload.json` 의 `streams` 에 다음이 기록됩니다 (생성의 분기 조건이 아니라 설명용 값입니다).

- `exact_repeat_fraction`: 이전에 정확히 같은 벡터가 나온 요청의 비율 = 무한 용량 정확 일치 캐시의 상한 히트율.
- `group_revisit_fraction`: 이전에 같은 그룹이 나온 요청의 비율 = 무한 용량 이상적 근사 캐시의 상한.

그룹 1만 개 × 구성원 200, 읽기 100만이면 정확 반복 상한은 지수에 따라 약 0.21~0.64 입니다 [계산].
읽기 수가 줄면(예: `u50` 의 50만) 상한도 낮아집니다. 값은 세트마다 `workload.json` 에 따로 기록됩니다.
근사 캐시의 효과를 정확 일치 효과와 분리하려면 정확 히트와 근사 히트를 나누어 보고하고 캐시 용량을 제한한
비교를 하세요.

## 사용법

환경: conda `toucann` (설정은 `conda/environment.yml`).

```bash
# 1) 공유 베이스 세트 (한 번만). config/base_set.example.ini 를 복사해 경로를 고친다.
script/build_base_set.sh my_base_set.ini

# 2) 워크로드 묶음 (target_overlap 목록 × group_size 목록 × update_percents 목록의 조합마다 세트 하나)
script/build_workload.sh my_workload.ini

# 3) (선택) 끝난 묶음에 새 겹침이나 새 그룹 크기의 풀만 추가: ini 에 existing = extend 를 쓰고 같은 명령을 실행
script/build_workload.sh my_workload.ini
```

**베이스 세트는 원본 파일을 앞에서 뒤로 한 번만 순차로 읽어서 만듭니다.** 행 번호(base, 삽입 후보,
예약 질의)는 먼저 한꺼번에 정하고(`partition.py`), 그 행들만 청크(기본 약 256MiB) 단위로 꺼냅니다.
삽입 후보는 무작위 순서로 정해져 있지만 파일에서는 오름차순으로 만나고, 메모리(많으면 임시 파일)에
삽입 순서의 자리로 모았다가 마지막에 순서대로 씁니다. 필요한 행이 없는 구간은 읽지 않습니다. 10억 행(128GB)
파일을 하드디스크에서 만들 때, 무작위 순서나 memmap으로 읽으면 수 시간이 걸리지만 이 방식은 파일을 한 번
읽는 시간(85MB/s에서 약 25분)입니다. 만들어지는 파일은 이전 구현과 바이트 단위로 같습니다 (골든 해시 테스트).
`base-set` 은 진행률을 stderr 에 5% 단위로 적습니다.

`device = gpu` 이면 정확한 정답을 GPU(cupy)로 계산합니다. 이 머신은 공유 자원이므로 가드로 한가한지
확인한 뒤 실행하세요 (`script/build_workload.sh` 상단 주석 참고). `device = cpu` 는 결과가 같고 훨씬 느립니다.

### 머신 자원 설정 (`[parallel]`)

| 설정 | 기본값 | 의미 |
|---|---|---|
| `gpus` | `1` | 쓸 GPU (`nvidia-smi` 번호). `auto` = 비어 있는 GPU 전부, `none`, `0,1`. 지정한 GPU가 사용 중이면 **오류** (조용히 CPU로 바뀌지 않음) |
| `gpu_max_used_mb` | `1024` | 이보다 적게 쓰는 GPU를 "비어 있다"고 봄 |
| `workers_per_gpu` | `1` | GPU당 워커 프로세스. 같은 GPU의 프로세스는 번갈아 실행될 뿐이라 1 이 적당함 |
| `cpu_workers` | `auto` | N2 풀 생성·해시·파일 쓰기·CPU 정답용 프로세스 수. `auto` = `numa_node` 의 물리 코어 수 (이 머신 node 1 은 16) |
| `numa_node` | `1` | 이 프로세스와 워커를 그 노드의 CPU에 고정. `none`, `auto`(GPU가 붙은 노드), 번호 |

- 기본값은 이 머신(GPU 1이 NUMA node 1에 붙어 있음)의 값입니다. **다른 머신에서 GPU나 노드가 없으면
  오류**로 멈추며 설정 이름을 알려 줍니다. `device = cpu` 이면 GPU 설정은 무시됩니다.
- `base_batch_rows`, `query_chunk_rows` 는 `auto` 가 기본입니다. 선택한 GPU의 여유 메모리의 60%
  (워커당 최대 8 GiB)를 쌍당 약 40바이트로 나눠 정하고, 메모리가 모자라 실패하면 블록을 절반으로 줄여
  다시 합니다. 정수형 데이터에서는 결과가 이 값에 의존하지 않습니다. 실제로 쓴 값은 `workload.json`
  에 기록됩니다.
- 시작 전에 호스트 메모리를 추정해 모자라면 데이터를 읽기 전에 이유와 함께 멈춥니다.
- 워커는 `spawn` 으로 시작하고 BLAS 스레드를 1 로 고정하며, 결과 파일은 **워커 수와 무관하게 같습니다**
  (테스트로 확인).

설정 항목의 설명은 `config/base_set.example.ini`, `config/workload.example.ini` 에 있습니다.
`workload.example.ini` 에는 프로그램이 읽는 **모든 옵션**이 (용도, 허용값, 기본값과 함께) 활성 줄 또는
`;` 주석 줄로 적혀 있고, 빠진 옵션이 없는지 테스트(`test_cli.py`)가 확인합니다.

## 검증

```bash
cd python && python -m pytest tests                       # 단위·종단·골든 테스트 (385개)
cd .. && python python/tests/mutation/run_mutations.py --jobs 6   # 고의 오류 주입 검사 (171개)
```

- 종단 테스트는 **출력 파일만 읽어** 독립 float64 참조 구현으로 모든 정답 파일을 다시 계산해 비교합니다
  (`python/tests/reference.py`). 우주 목록으로 못 만드는 경우(fallback)도 목록을 일부러 짧게 해서 확인합니다.
- **골든 해시 테스트** (`test_golden.py`): 우주 목록과 병렬 생성을 넣기 **전** 코드가 만든 모든 출력 파일의
  sha256 (`python/tests/golden/golden_hashes.json`)을 새 코드가 그대로 재현해야 합니다 (CPU 워커 1, 2, 4).
  numpy 난수에 의존하므로 numpy 버전이 다르면 건너뜁니다.
- 병렬 테스트: 워커 수·장치(CPU/GPU)·GPU당 워커 수를 바꿔도 출력 파일이 같습니다. GPU 테스트는 비어 있는
  GPU가 없으면 건너뜁니다 (GPU 2개 테스트는 두 GPU가 모두 보이고 비어 있을 때만 실행).
- mutation 검사는 `python/tests/mutation/mutations.py` 의 고의 오류를 하나씩 주입한 복사본에서 테스트가
  실패하는지 확인합니다. 원본 소스는 바뀌지 않으며, 실행 전에 항상 원본이 통과하는지 먼저 봅니다.
  `--jobs N` 으로 여러 개를 동시에 검사할 수 있습니다.

## 알려진 한계

- 합성 워크로드입니다. 유사 질의 묶음의 실제 크기·개수 분포를 알지 못합니다.
- 이 라운드에서는 SIFT 1M 등 실제 데이터로 생성을 실행하지 않았습니다. GT 계산 시간은 실측하지 않았습니다.
- 삭제는 균일 무작위만 지원합니다 (질의와 정렬된 삭제는 없음).
- `uniform_unique` 는 편중이 없는 스트림입니다. 편중이 있는 중복 없는 스트림은 구조적으로 불가능합니다.
- `variants = none` 에서 중복 없는 스트림의 길이는 주어진 질의 수 이하로 제한됩니다.
- 우주 목록 방식은 질의 그룹(기본 524,288개)마다 우주를 한 번 훑습니다. 100M 규모의 디스크 읽기는
  그만큼 base 를 읽으므로 크고, 이 규모는 시험하지 않았습니다.
- 우주 목록의 길이는 "삭제가 균일하고 삽입 순서가 무작위"라는 가정으로 정합니다. 삭제가 질의의 이웃에
  몰리는 정책이 생기면 직접 훑는(fallback) 횟수가 늘어 느려지지만 결과는 틀리지 않습니다.
- float 임베딩에서는 우주 목록의 블록 구성이 예전 방식과 달라 거리의 마지막 비트가 다를 수 있습니다.
  정수형 데이터(uint8, int8)는 출력 파일이 예전 방식과 비트 단위로 같습니다 (골든 해시 테스트).
- 같은 베이스 세트를 공유하는 워크로드들은 데이터가 같아 짝 비교에는 좋지만 독립 표본이 아닙니다.
- 묶음 추가는 새 겹침과 새 그룹 크기에 한정됩니다. 갱신 비율, Zipf 설정, 요청 수, 평가 설정을 바꾸는 것은
  새 묶음으로 만들어야 합니다 (우주 목록의 범위와 모든 풀의 스트림이 달라지기 때문).
- 모든 풀을 메모리에 한꺼번에 올립니다. 풀 합계는 겹침 수에 비례해 늘어납니다 (사전 메모리 검사가 추정해
  모자라면 데이터를 읽기 전에 멈춥니다). 겹침이 아주 많으면 겹침별로 나눠 처리해야 합니다 (이 구현에는 없음).
- 형식 2(겹침 단계가 없는 `g100/...`) 묶음은 읽기만 되고 추가할 수 없습니다. 이름 바꾸기 이전(migration)은 없습니다.
- 추가 모드의 동시 실행 방지는 같은 머신의 프로세스 번호로 판단합니다 (네트워크 파일 시스템을 여러 머신에서
  공유하며 동시에 추가하는 경우는 막지 못합니다).
